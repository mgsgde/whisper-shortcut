### `gemini-3.1-pro-preview` hangs on short dictations — added to the benchmark, then found broken

Added to `MODELS` after this report's first draft (with the `minimal`→`low` thinking-level clamp
mirrored from `geminiTranscriptionGenerationConfig`, since Pro 400s on `minimal`). The first run
showed the 1.3 s case failing every time, which turned out to be real and reproducible:

| Request sent with the 1.3 s clip | Result |
|---|---|
| App's live dictation prompt + 36-term glossary (what we ship) | **4/4 no response** — 3× 90 s timeout, 1× **300 s, zero bytes received** |
| App's dictation prompt, first half only (persona + verbatim rules) | no response at 90 s |
| App's dictation prompt, second half only ("transcription task only…") | no response at 90 s |
| **Neutral 436-char transcription prompt, no wording shared with ours** | **2/2 no response** at 90 s |
| Same dictation prompt via **`:streamGenerateContent?alt=sse`** | **2/2 no response** at 90 s, zero bytes — not even an SSE header |
| App's dictation prompt, non-streaming, **re-run one hour later** | no response at 90 s |
| `"Transcribe the audio verbatim."` + the same 36-term glossary block | **HTTP 200, 7.7 s**, correct |
| `"Transcribe the audio verbatim."` (control, interleaved with the failures) | **HTTP 200, 6.3 s / 5.4 s / 5.9 s** |

Controls passing *between* the failures, including an hour later, rule out quota, rate limiting and
transient windows. Four things this is **not**: not the glossary (it passes with a trivial
instruction), not one bad sentence (both halves fail alone), not our prompt at all (an unrelated
436-char instruction fails the same way), and not response assembly (streaming never emits a first
token either). What remains is Pro + a substantial transcription instruction + very short audio.
Longer clips mostly survive (8.2 s: 1 of 3; 21.3 s: 3 of 3), so severity falls off with duration.
Silence and glossary suites were not run against Pro — it cannot complete the short case.

Because the neutral prompt fails too, **there is no prompt wording that fixes this**, and because
streaming fails identically there is no request-shape fix either.

**This reaches users.** `TranscriptionModels.swift:136` routes Pro to non-streaming
`:generateContent`, and `SpeechService.Constants.resourceTimeout` is 300 s — the same ceiling that
returned zero bytes here. A user who picks Gemini 3.1 Pro for dictation and says something brief
gets a five-minute hang and then a timeout error. It is worth noting this is the same short-audio
blind spot that makes Flash-Lite confabulate (`discardingImplausibleTranscript`); Pro appears to
stall on it instead.

Both follow-ups this section originally left open have since been run and are folded into the table
above: a differently-worded instruction hangs too, and streaming hangs too. What is still untried is
Google's Live API — a different product surface the app's `:generateContent` path cannot call
anyway, so it cannot rescue this model for dictation.

**The systemic result is unchanged and is the most important number in this report: all three
non-Gemini cloud models leak zero invented transcripts; every Gemini tier leaks 3–9 of 9. Our
default is on the leaking side.** `gemini-3.1-flash-lite` improved from 6/9 to 3/9 — real progress,
but still not zero.

### Answers to the two questions

**1. Is any model we ship Pareto-dominated?**
**No.** Every model still selectable is on the frontier for its provider. The three that *were*
dominated — `gpt-5.5`, `gpt-5.4`, the `grok-4.20-*` pair — plus `claude-opus-4-8` are all already
hidden by `chatReplacement`, so they never reach a picker.

The one model I would still remove is **`gpt-4o-transcribe`**, and the honest reason is not
domination: it leaks **8/9** invented transcripts to the clipboard, costs more than `gpt-transcribe`,
and its one surviving axis (prompt instruction-following) is covered better and cheaper by
`gpt-4o-mini-transcribe`. Call it a quality removal, not a Pareto prune.

**2. Is any model missing that should be there?**
**No new frontier model at any provider this month.** *(probe)*-verified against all four live model
lists. Nothing to add.

Two models that exist and are deliberately **not** recommended:
- `gpt-audio-mini` — deprecated upstream (shutdown 2027-01-20) *and* scores below `gpt-audio-1.5`.
- `gpt-4o-transcribe-diarize` — serves *(probe)*, but the one observation I have shows worse glossary
  than the model we already ship. Benchmark first.

The standing default question is unchanged: **`gpt-transcribe` beats the transcription default
`gemini-3.1-flash-lite` on every measured axis** — 0/9 vs 3/9 silence leaks, 100% vs 94% glossary,
and faster at 1.3 s (802 vs 1626 ms), 8.2 s (915 vs 1213 ms) and 21.3 s (1558 vs 1591 ms). It is
already in the lineup; it is simply not the default and not marked recommended.

  named replacement `gemini-3.5-flash-lite` leaks 7/9 vs 3.1's 3/9, scores 85% vs 94% glossary, and
  is 1.3–3.1× slower. **The measurement wins — do not follow Google's replacement pointer.**
  Revisit when a better Flash-Lite ships, or by early 2027.
- **`gemini-3.1-pro-preview` — benchmarked, found broken, withdrawn from the dictation picker.
  APPLIED.** Adding it to the benchmark produced something worse than "no data": with the prompt we
  actually ship it returns nothing at all on short dictations, 4/4, including one 300 s attempt that
  received zero bytes (full detail in the benchmark section). Since the app's own timeout is also
  300 s, offering it meant a five-minute hang for anyone who dictated a short utterance.

  Implemented as `TranscriptionModel.isSelectableForDictation`, mirroring the existing
  `PromptModel.isSelectableInChat` pattern, plus `migrateLegacyTranscriptionRawValue` forwarding
  **both** Pro slugs to `gemini-3.1-flash-lite`. The enum case is deliberately **kept**: deleting it
  broke the build, because `PromptModel.asTranscriptionModel` borrows this enum to resolve the
  Gemini endpoint for Dictate Prompt (`SpeechService.swift:719`) and Smart Improvement
  (`ContextDerivation.swift:17`) — returning nil there would have broken chat for Pro users while
  fixing dictation. Pickers now default to `selectableForDictation` instead of `allCases`; both
  call sites used the default, so nothing else changed. It was also removed from the benchmark's
  `MODELS` (re-add it only to check whether Google has fixed it).

  **Untested and worth a follow-up:** `PromptModel.gemini31Pro` is still offered for chat and
  Dictate Prompt, and Dictate Prompt also sends short audio. If the stall is a property of the model
  on brief audio rather than of the transcription path, that mode may hang the same way. Nobody has
  measured it.

**Not recommended, explicitly:** removing `gpt-4o-transcribe` on Pareto grounds. If you remove it,
the honest justification is the 8/9 leak rate, not domination.

## Open questions

1. **An Anthropic key in `.env` — second month asking.** Five `PromptModel` cases are unguarded by
   the audit loop, and `claude-opus-5` shipped last month on doc evidence alone, never probed. This
   is still the single biggest blind spot in the report.
2. **Should the transcription default become key-conditional?** Unchanged from last month, and the
   gap narrowed slightly (3.1 Flash-Lite went 6/9 → 3/9) but did not close. Conditional-default code
   vs. just flipping `isRecommended` — your call.
3. **Is the Gemini silence-hallucination rate a model problem or a gate problem?** Every Gemini tier
   leaks 3–9 of 9 while all three non-Gemini cloud models leak zero. Two months of the same pattern
   points at `TextProcessingUtility`'s plausibility gates as much as at the models — worth a separate
   look rather than a model swap.
4. **`gpt-5.4-mini` vs `gpt-5.6-luna` deserves a measurement.** Luna wins price-in, price-out and
   context; 5.4-mini survives purely on OpenAI's tier labelling. One benchmark would turn a
   marketing-copy argument into a real one.
5. **The Dictate Prompt JSON leak.** One `gpt-audio-1.5` run emitted raw `{"edits": [...]}` into the
   scored output. If that reaches the clipboard in the shipped app it is a user-visible bug — worth
   confirming whether the app's post-processing catches it, independently of any model choice.
