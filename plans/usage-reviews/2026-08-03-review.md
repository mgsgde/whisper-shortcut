## Proposed (added to ledger)

**I1 — `[code]` `ChunkedDictateRecorder` blocks the main thread on `AVAudioRecorder.record()`/`.stop()`.**

Two watchdog hangs this week, both ≥4s, both rooted in the same class:

- `hang-20260728-165723.txt`, 16:57 — mid-recording chunk rotation. Stack: `NSTimer` (metering) → `beginSession` → `rotateChunk` → `AVAudioRecorder.stop()` → `AudioQueue::AwaitAllPendingCallbacks` (blocking wait on the audio queue's I/O thread).
- `hang-20260802-170842.txt`, 17:08 — starting a new dictation via Fn push-to-talk. Stack: `fnPushToTalkStart` → `toggleTranscription` → `startRecording` → `startChunkRecording` → `beginSession` → `AVAudioRecorder.record()` → `AudioQueueXPC_Bridge::Start`.

Both are `ChunkedDictateRecorder.swift`: `beginSession()` (record, line ~219) and `rotateChunk()` (stop, line ~282) call the `AVAudioRecorder` APIs directly wherever they're invoked from — a main-thread `NSTimer` callback for rotation, and the main-thread push-to-talk/menu path for start. Both `AudioQueueStart`/`AudioQueueStop` can block synchronously on CoreAudio's I/O thread for multiple seconds, which is exactly what the watchdog caught. Fix: dispatch the record/stop calls to a dedicated background queue.

This is a different hang variant than the ones `analyze-chat-freeze` already tracks (those are chat-streaming hangs) — this one fires during dictation, not chat.
